Writing a widget

For anyone who knows some JavaScript and wants a display, or a tool, that Simile on the web does not have.

A widget is a panel in the app: the diagram, the plotter and the sliders are all widgets. You can write your own, add it with Widgets ▸ Add a widget…, and it appears in the Widgets menu beside the built-in ones, opening for the current model as they do. You can share it with others by putting it online.

A widget is one JavaScript file. You do not need to install anything or build anything. If you would rather not write it yourself, Widgets ▸ Instructions for an AI assistant… gives you text to paste into a chat with an AI assistant, which then writes the file for you. Everything below is in those instructions too.

1. The file

The whole file is one call to Sienna.widget. Here is a complete widget that rolls a die:

Sienna.widget({
  name: 'dice',                     // letters, digits and _, starting with a letter
  label: 'Dice',                    // its entry in the Widgets menu
  notes: 'Rolls a die.',            // shown to whoever adds it
  author: 'Your name', version: '1.0',
  contract: 1,                      // the version of these rules it follows
  widget: {
    options: { sides: 6 },
    _create: function () {
      var face = $('<div>').css({ fontSize: '48px', textAlign: 'center' }).text('–');
      var roll = $('<button type="button" class="slx-chrome">').text('Roll');
      roll.on('click', () => face.text(1 + Math.floor(Math.random() * this.options.sides)));
      this.element.append(face, roll);
    },
  },
});

It is loaded as an ordinary script, so there are no modules: no import or export. The page already has jQuery ($) and the global Sienna. Plain JavaScript that a current browser runs as it is, with no build step.

FieldWhat it is
nameRequired, and unique. A name the app already uses, or any jQuery method name (show, data…), is refused, so pick a distinctive one.
label, titleThe menu entry, and the panel's title (default: the label).
role'display' opens it among the model's displays in its Simulation window, as a plot is. Leave it out for a window of its own.
optionsDefault options.
notes, author, versionShown before and after it is added, and in Manage added widgets.
contractThe version of these rules (now 1). A widget needing a newer one than the app has is refused with a message.
widgetThe widget itself: a jQuery UI widget prototype. The app defines and registers it for you; do not call $.widget yourself.

2. Inside the widget

  • this.element is the panel's content (a jQuery object): build everything inside it. this.options holds the options.
  • Give toolbars and controls the class slx-chrome. When the user shrinks a panel to a thumbnail, those are hidden and the rest stays.
  • The panel can be resized at any time. To redraw to fit, call this._watchPanelResize(fn) once in _create.
  • To keep a choice across a reload of the app, return it from a method state(), as an object whose keys are option names. It is saved with the panel and given back as options next time.
  • _destroy must undo whatever _create did outside this.element: timers, subscriptions, listeners on the document.
  • Style with inline styles, or one <style> element of your own whose classes all start with your widget's name. Never style bare elements (button { … }) or the app's own slx- classes: that changes the whole app.

3. Showing a running model

Most widgets people want are displays: something the plotter does not show, or not the way you want. A display listens to the run; the run control loads and runs the model. In _create:

this._sim = Sienna.Simulation.forWidget(this._ref());
this._off = this._sim.subscribe((e) => this._onEvent(e));

and in _destroy, this._off() and a removeTarget for each target you added. That object is the whole interface, and the only part of the simulation a widget should use:

MemberWhat it is
baseNull while no model is loaded for this panel's model. Show that ("Run the model to see values").
scalarComponents()[{ id, label, units }]: the variables that are one number. label is the path, such as Trees/biomass.
memberComponents()The same for variables with a value per instance: in a population, a fixed-membership submodel, or an association.
addTarget(owner, id)Ask for a variable's values as the model runs. owner is any string of yours, one per thing you show; adding again with it replaces the variable. removeTarget(owner) stops it.
query([id])The values now, without running: a promise of { id: value }. Rejects when no model is loaded.
subscribe(fn)Hear events (below). Returns the function that stops it.
time()The model time now.
runLength()The length of the run.
unitNameThe time unit's name (often just "unit").
status'idle', 'loading', 'ready', 'running' or 'error'.

The events:

EventWhen, and what it carries
dataOnce per logged time step: { time, values, reset }, with values[id] for each target. reset: true means the run went back to its start, so clear any history you keep.
describeA model has just been loaded. Ids change between loads: read the lists again, find the user's choice again by its label, and add the target again. Save a choice by label, never by id.
status{ status }, as above. When base is null, nothing is loaded.
progress, settingsHow far through the run, and the run's settings changed. Usually ignored.

A value is a number; an array for a fixed membership (element 0 is instance 1); an object for a population, { '3': v, '7': v }, keyed by the members' own numbers, which they keep for life; an object for an association, { '3,17': v }, one number per role; or null.

A complete display, about sixty lines, is examples/widgets/big-number.js: one chosen variable, shown large, updated as the model runs. It was written from the instructions for an AI assistant alone, and is the best place to start a display of your own.

4. Reading the model itself

A panel belongs to one model. this._ref() is its path, and this._model() the model spec: name; nodes, { id: { type, label, parent, props } }, where type is 'stock', 'variable', 'valve' (a flow's rate), 'condition' and so on, and props holds the fields (initial, rate, value, units…); submodels; and arcs. Call this._watchModel(fn) once in _create to hear every change, including undo.

Read it; do not change it in place. A widget that is meant to edit the model writes with this._set('sub/path', value), inside this._action('what', payload, function () { … }), so the edit is saved and undone as one step.

5. Trying it out

Widgets ▸ Add a widget… takes the file's address, or lets you select the file. When the app is opened from your own disk, its path works (file:///home/you/widgets/dice.js). On the web, the app cannot read a file on your computer by its path, so select the file instead; it is then kept with your settings.

Errors are shown on the panel, with the file and line: a red bar for an error while the widget runs, or a message in place of the widget if it failed as it started. Errors in a file added by its path are hidden by the browser, so a mistake that stops the file running at all (a missing bracket, say) is reported without its line. Select the file instead, or open the browser's console (F12), to see where it is.

After you edit the file, press Reload: on the red bar, on the message, or in Widgets ▸ Manage added widgets…. It runs the file again and re-makes the widget's open panels, keeping what state() kept. A selected file has to be selected again, because a page cannot re-read a file by itself.

6. Sharing it

Put the file anywhere on the web that serves it as it is, such as a GitHub repository published with GitHub Pages, and give people its address. To give several at once, put a toolkit beside them, a file such as toolkit.js:

Sienna.toolkit({
  name: 'my-displays', label: 'My displays',
  notes: 'Three displays for population models.', author: 'Your name', version: '1.0',
  widgets: ['big-number.js', 'histogram.js', 'https://example.org/w/clock.js'],
});

Relative addresses are relative to the toolkit's own file, so the folder can be moved, or put online, as a whole. People add it with Widgets ▸ Add a toolkit…, see its list, and load the widgets only if they agree.

7. What a widget must not do

An added widget runs inside the app with everything the app has: it could read, change or delete the user's saved models. People are warned of that before they add one, and asked to add only widgets from people they trust. To deserve that trust:

  • No network access the user did not ask for: no sending data elsewhere, no analytics, no loading scripts from other sites.
  • Never touch localStorage, sessionStorage or IndexedDB, where the user's work is kept. Use state() and the model methods above.
  • Do not change Sienna, $ or anything else global, or the page outside this.element.
  • No alert, confirm or prompt: show messages in the panel.
  • A display reads the run and never drives it.
